## 프로젝트 소개

REDRED는 웹 보안 실습을 위해 **가상의 마케팅 회사 `Cortis`에서 사용하는 취약한 사내망 웹 서비스**를 구축하고, 주요 웹 취약점을 탐지·검증한 모의해킹 프로젝트입니다.

Apache, PHP, MariaDB를 이용해 임직원 로그인, 부서 정보, 사내 자료실, 공지사항 및 파일 업로드 기능을 구현했습니다. 이후 Kali Linux와 Burp Suite를 활용하여 취약점을 수동으로 검증하고, OpenAI API 기반의 `AI Scanner`를 통해 진단 후보 분석과 보고서 작성을 자동화했습니다.

본 프로젝트에서는 AI의 분석 결과를 곧바로 확정된 취약점으로 처리하지 않습니다. AI Scanner가 탐지한 항목을 보안담당자가 직접 재현하고 증적을 확인한 후 최종 판정을 내리는 **Human-in-the-loop 방식**을 적용했습니다.

## AI Scanner

### 개발 목적

AI Scanner는 보안담당자를 완전히 대체하는 자동 공격 도구가 아니라, 다음 업무를 보조하기 위한 목적으로 개발했습니다.

- 대상 페이지의 1차 자동 분석
- 취약점으로 의심되는 항목 식별
- HTTP 요청과 응답 차이 분석
- 취약점 후보와 수동 검증 절차 정리
- 보안담당자가 제공한 증적 자료의 구조화
- 최종 보고서 및 시큐어 코딩 가이드 초안 생성
- 보고서 PDF 변환

### 활용 흐름

1. 보안담당자가 AI Scanner를 통해 대상 페이지의 1차 스캔을 실행합니다.
2. AI Scanner가 페이지를 분석하고 취약점 후보가 포함된 진단 가이드를 작성합니다.
3. 보안담당자가 해당 진단 가이드를 바탕으로 취약점을 직접 검증합니다.
4. 검증 과정에서 요청·응답, 화면 캡처 및 재현 결과 등의 증적을 확보합니다.
5. 확보한 증적과 수동 검증 결과를 AI Scanner에 등록합니다.
6. AI Scanner가 자동 분석 결과와 수동 증적을 함께 검토하여 다시 진단합니다.
7. 검증된 결과를 바탕으로 고객사 전달용 최종 모의해킹 보고서를 생성합니다.
8. 취약점별 보완 방법을 정리한 시큐어 코딩 가이드를 생성합니다.
9. 생성된 문서를 PDF로 변환하고 보안담당자가 최종 내용을 검수합니다.

### 취약점 판정 상태

AI Scanner가 발견한 항목은 다음 단계로 관리했습니다.

```text
CANDIDATE
AI Scanner가 취약점 가능성을 식별한 상태
        ↓
REVIEW
보안담당자가 정상 요청과 의심 요청을 비교하고 재현하는 상태
        ↓
CONFIRMED
수동 재현과 증적을 통해 실제 취약점으로 확인된 상태
        ↓
REJECTED
재현되지 않거나 정상 동작으로 판단되어 제외된 상태
```

> [!IMPORTANT]
> AI Scanner의 자동 분석 결과는 확정 판정이 아닌 취약점 후보입니다.  
> 최종 보고서에는 보안담당자가 직접 재현하고 증적을 확인한 결과만 검증된 취약점으로 포함합니다.

## 취약점별 분석

### 1. SQL Injection

#### 개요

사용자 입력값이 SQL 쿼리에 직접 포함되는 로그인, 검색 및 데이터 처리 기능을 대상으로 점검했습니다.

페이지마다 사용되는 SQL 쿼리와 괄호, 조건문 및 조회 컬럼 수가 달랐기 때문에 하나의 입력값을 모든 페이지에 동일하게 적용할 수 없었습니다. 각 페이지의 쿼리 구조와 입력 파라미터를 개별적으로 분석한 후 취약점을 검증했습니다.

#### 주요 점검 대상

| 페이지 | 주요 파라미터 | 점검 내용 |
| --- | --- | --- |
| `login.php` | `employee_number`, `password` | 임직원 로그인 인증 우회 가능성 |
| `department_members.php` | `dept`, `keyword` | 부서원 검색 조건 및 부서 범위 우회 |
| `department_resources.php` | `dept`, `keyword` | 부서 자료 검색 조건 및 범위 우회 |
| `resource.php` | `keyword` | 공용 자료 검색 조건 우회 |
| `notices.php` | `keyword`, `id` | 공지 검색 및 수정·삭제 조건 조작 가능성 |
| `delete.php` | `id` | 자료 삭제 대상 조건 조작 가능성 |

#### 확인된 영향

- 임직원 로그인 인증 우회
- 부서 범위를 벗어난 직원 정보 조회 가능성
- 사내 자료 및 공지정보 노출
- 데이터베이스 컬럼 및 구조 추론
- 임직원 계정정보와 중요 데이터 노출 가능성
- 조건 조작을 통한 복수 데이터 수정·삭제 가능성
- 상세한 데이터베이스 오류정보 노출

> 데이터 변경 및 삭제가 발생할 수 있는 점검은 테스트 데이터와 격리된 환경에서 제한적으로 수행했습니다.

#### 발생 원인

- 사용자 입력값을 SQL문에 직접 결합
- Prepared Statement 또는 Parameterized Query 미사용
- 숫자형 식별자에 대한 데이터 타입 검증 부족
- 상세한 데이터베이스 오류 메시지 노출
- 데이터베이스 계정의 과도한 권한

#### 점검 과정에서 얻은 교훈

초기에는 일부 입력값으로 공격이 재현되지 않아 SQL Injection이 불가능한 것으로 오해했습니다. 이후 페이지마다 SQL문의 구조와 조건 결합 방식이 다르다는 점을 확인하고, 각 쿼리에 맞춰 검증한 결과 여러 페이지에서 취약점을 확인할 수 있었습니다.

이를 통해 자동화된 페이로드 반복보다 **서버 측 쿼리 구조와 응답 차이를 이해하는 과정이 중요하다**는 점을 확인했습니다.

---

### 2. Stored XSS

#### 개요

공지사항 제목과 내용처럼 사용자의 입력값이 데이터베이스에 저장된 후 다른 사용자에게 다시 출력되는 영역을 점검했습니다.

출력값에 적절한 HTML Encoding이 적용되지 않아 저장된 입력값이 브라우저에서 스크립트로 해석될 수 있음을 확인했습니다.

#### 주요 발생 위치

- 공지사항 등록 및 수정 화면의 제목
- 공지사항 등록 및 수정 화면의 내용
- 공지사항 목록
- 공지사항 상세 페이지

#### 예상 영향

- 공지사항을 열람한 임직원의 브라우저에서 스크립트 실행
- 세션 및 사용자 정보 노출
- 사용자 권한을 이용한 비정상 요청 수행
- 피싱 페이지 또는 악성 사이트로 이동
- 사내 게시물 및 페이지 변조

#### 발생 원인

- 사용자 입력값에 대한 검증 부족
- 출력 시 HTML Encoding 미적용
- 사용자 작성 콘텐츠와 실행 가능한 코드의 구분 부족
- 세션 쿠키 및 브라우저 보안 정책 미흡

---

### 3. Reflected XSS

#### 개요

검색어가 응답 페이지에 그대로 출력되는 기능을 대상으로 Reflected XSS를 점검했습니다.

조작된 검색어가 적절한 인코딩 없이 화면에 반영될 경우, 사용자가 해당 요청에 접근했을 때 브라우저에서 스크립트가 실행될 수 있음을 확인했습니다.

#### 주요 발생 위치

- `department_members.php`의 `keyword`
- `department_resources.php`의 `keyword`
- `resource.php`의 `keyword`
- `notices.php`의 `keyword`

#### 예상 영향

- 조작된 링크를 통한 악성 스크립트 실행
- 임직원 세션 및 브라우저 정보 노출
- 피싱 및 사용자 행위 유도
- 사용자 권한을 이용한 비정상 요청

---

### 4. File Upload를 통한 WebShell 실행

#### 개요

공용 자료실, 부서 자료실 및 공지사항의 첨부파일 업로드 기능을 대상으로 파일 검증과 저장 방식의 안전성을 점검했습니다.

서버가 파일 확장자, MIME Type 및 실제 내용을 충분히 검증하지 않고 업로드 파일을 웹에서 직접 접근 가능한 경로에 저장할 경우, 서버에서 실행 가능한 WebShell이 업로드될 수 있습니다.

#### 주요 점검 대상

| 페이지 | 업로드 파라미터 | 저장 위치 | 주요 취약점 |
| --- | --- | --- | --- |
| `upload.php` | `file` | `uploads/resource/` | 원본 파일명 사용, MIME Type 검사 미흡, 블랙리스트 방식 |
| `department_resources.php` | `resource_file` | `uploads/departments/{dept}/` | 제한된 확장자만 차단, 대소문자 변형 우회 가능 |
| `notices.php` | `attachment` | `uploads/notices/` | 제한된 확장자만 차단, 대소문자 변형 우회 가능 |

#### 검증 결과

격리된 실습 환경에서 WebShell 파일을 업로드한 후 생성된 파일 URL에 직접 접근했습니다.

그 결과 파일이 다운로드되거나 내용만 표시되는 것이 아니라 서버에서 실행되었으며, 실행 결과로 웹 서버 프로세스의 계정인 `www-data`가 출력되는 것을 확인했습니다.

이를 근거로 공격자가 업로드한 파일을 통해 웹 서버 프로세스의 권한 범위에서 시스템 명령을 실행할 수 있다고 판단했습니다.

#### 발생 원인

- 허용 목록이 아닌 블랙리스트 기반 확장자 검증
- 특정 소문자 확장자만 차단하여 대소문자 변형 허용
- MIME Type 및 파일 시그니처 검증 미흡
- 원본 파일명을 그대로 사용
- 업로드 파일을 웹에서 직접 접근 가능한 경로에 저장
- 업로드 디렉터리에서 PHP 스크립트 실행 허용

#### 예상 영향

- 웹 서버 권한으로 시스템 명령 실행
- 서버 내부 파일 및 설정정보 열람
- 데이터베이스 접속정보 등 중요정보 노출
- 서버 파일 및 웹 페이지 변조
- 추가 악성 파일 업로드
- 내부 시스템 공격을 위한 거점 확보
- 조건에 따른 웹 서버 제어권 탈취

> [!NOTE]
> 본 취약점은 파일 다운로드 취약점이 아니라, **파일 업로드 검증 미흡으로 인한 WebShell 업로드 및 서버 측 실행 취약점**입니다.

## AI 진단 결과 분석

### 자동 탐지와 수동 검증

AI Scanner는 자동 스캔을 통해 요청과 응답의 차이를 분석하고 SQL Injection 등의 취약점 후보를 식별했습니다.

예를 들어 로그인 페이지에서 특정 입력을 전송한 후에도 응답 상태와 리다이렉트 위치가 정상 요청과 유사하게 나타난 경우, AI Scanner는 해당 항목을 즉시 확정하지 않고 `CANDIDATE`로 분류하여 추가 검증 대상으로 전달했습니다.

보안담당자는 Burp Suite를 이용해 다음 내용을 비교했습니다.

- 정상 요청과 의심 요청의 상태 코드
- 응답 길이와 본문 유사도
- 리다이렉트 위치
- 로그인 상태 및 권한 변화
- 서버의 실제 데이터 처리 결과
- 동일 요청의 재현 가능성

### 미탐 사례

수동 점검에서는 File Upload를 통한 WebShell 실행 취약점을 확인했지만, AI Scanner의 자동 스캔에서는 해당 취약점을 발견하지 못했습니다.

이는 실제 취약점이 존재함에도 자동 진단에서 식별하지 못한 **미탐(False Negative)** 사례입니다.

#### 미탐 원인으로 분석한 내용

- 파일 업로드 요청은 일반 입력값과 다른 `multipart/form-data` 구조를 사용
- 파일 업로드 이후 생성되는 저장 경로를 추가로 추적해야 함
- 업로드 성공 여부만으로는 서버 측 실행 가능성을 판단하기 어려움
- WebShell 실행 여부를 확인하려면 업로드 후 URL 접근과 응답 분석이 필요
- 확장자 대소문자 및 서버 설정에 따른 실행 여부를 함께 검증해야 함

#### 개선 방향

- 파일 업로드 폼과 파일 파라미터 자동 식별
- 허용 확장자와 차단 정책 분석
- MIME Type과 실제 파일 내용의 불일치 점검
- 업로드 이후 생성된 파일 경로 추적
- 웹 루트 내부 저장 및 URL 직접 접근 여부 확인
- 안전한 테스트 파일을 이용한 서버 측 실행 가능성 검증
- 업로드 디렉터리의 실행 권한과 웹 서버 설정 분석

### 신규 취약점 후보 식별

AI Scanner는 자동 분석 과정에서 기존 점검 시나리오에 포함되지 않았던 추가 취약점 후보를 제시했습니다.

다만 자동으로 제시된 항목은 그 자체로 실제 취약점이라고 확정하지 않았으며, 수동 재현과 증적 확인을 거쳐 최종 보고서 포함 여부를 결정했습니다.

### 프로젝트에서 확인한 AI의 역할

| AI가 효과적으로 보조한 영역 | 사람의 검증이 필요했던 영역 |
| --- | --- |
| 반복적인 페이지 및 요청 분석 | 실제 공격 성공 여부 확인 |
| 응답 차이를 기반으로 후보 식별 | 서비스의 정상 동작과 취약 동작 구분 |
| 취약점별 점검 절차 정리 | 권한과 업무 흐름을 고려한 영향 평가 |
| 수집된 증적의 구조화 | 오탐 및 미탐 판정 |
| 보고서와 대응 가이드 초안 생성 | 최종 문구, 위험도 및 고객 전달 내용 검수 |

본 프로젝트를 통해 AI는 보안담당자의 분석과 문서화를 보조할 수 있지만, 자동 진단만으로 모든 취약점을 탐지하거나 확정하기는 어렵다는 점을 확인했습니다.

## 보고서 자동 생성

AI Scanner는 자동 분석 결과와 보안담당자가 제공한 증적을 바탕으로 다음 문서를 생성하도록 구성했습니다.

### 1. Diagnostic Guide

자동 스캔에서 확인된 취약점 후보를 보안담당자가 검증할 수 있도록 정리한 문서입니다.

주요 포함 내용은 다음과 같습니다.

- 대상 URL
- HTTP Method
- 취약한 것으로 의심되는 파라미터
- 예상 취약점 유형
- AI Scanner의 신뢰도
- 요청 및 응답 특징
- 정상 요청과의 비교 결과
- 오탐 가능성
- 권장 수동 검증 절차
- 추가 확인이 필요한 보안 항목

### 2. Final Report

수동 검증과 증적 확인을 완료한 취약점만 정리한 최종 모의해킹 결과 보고서입니다.

주요 포함 내용은 다음과 같습니다.

- 진단 대상 및 범위
- 검증된 취약점 목록
- URI, Method 및 파라미터
- 위험도, CWE 및 OWASP 분류
- 자동 분석 근거
- 보안담당자의 수동 검증 결과
- 요청·응답 및 화면 증적
- 취약점으로 인한 영향
- 최종 판정 상태

### 3. Secure Coding Guide

수동 검증에서 확인된 취약점을 안전하게 개선할 수 있도록 작성한 대응 가이드입니다.

주요 포함 내용은 다음과 같습니다.

- 취약점 발생 원인
- 권장 대응 방안
- 소스코드 관점의 적용 방법
- 서버 및 데이터베이스 설정 개선
- 수정 후 재검증 방법
- 증적 화면 및 참고 내용

### 4. PDF 변환

생성된 진단 가이드, 최종 모의해킹 보고서 및 시큐어 코딩 가이드를 PDF로 변환하는 기능을 추가했으며, 문서와 증적 이미지가 정상적으로 포함되는 것을 확인했습니다.

| 생성 문서 | 출력 예시 |
| --- | --- |
| 진단 가이드 | `diagnostic_guide.pdf` |
| 최종 모의해킹 보고서 | `final_report.pdf` |
| 시큐어 코딩 가이드 | `secure_coding_guide.pdf` |

## 보안 대응 방안

### SQL Injection

#### 소스코드 관점

- Prepared Statement 및 Parameterized Query 적용
- SQL문과 사용자 입력값 분리
- 숫자형 식별자에 대한 타입 변환 및 범위 검증
- 입력값의 길이와 허용 형식 검증
- 동적 SQL문 사용 최소화
- 사용자에게 상세한 데이터베이스 오류를 노출하지 않도록 처리

#### 설정 및 권한 관점

- 애플리케이션별 데이터베이스 계정 분리
- 데이터베이스 계정에 최소 권한 적용
- 읽기 기능에서 수정·삭제 권한 제거
- 오류 및 비정상 쿼리 로그 기록
- 중요 데이터의 암호화 및 안전한 비밀번호 해시 적용

---

### XSS

#### 소스코드 관점

- 사용자 입력값을 서버 측에서 검증
- 출력 위치와 컨텍스트에 맞는 인코딩 적용
- HTML 출력 시 특수문자 변환
- 사용자 작성 HTML이 필요한 경우 검증된 Sanitizer 적용
- 신뢰할 수 없는 값을 DOM에 직접 삽입하지 않도록 제한

#### 설정 및 세션 관점

- Content Security Policy 적용
- 세션 쿠키에 `HttpOnly`, `Secure`, `SameSite` 적용
- 외부 스크립트 출처 제한
- 세션 만료 및 재인증 정책 강화

---

### File Upload 및 WebShell

#### 소스코드 관점

- 허용 목록 기반으로 업로드 가능한 확장자 제한
- 파일 확장자를 대소문자 구분 없이 정규화한 후 검증
- MIME Type과 실제 파일 시그니처 함께 확인
- 확장자와 파일 내용의 일치 여부 검증
- 서버가 생성한 임의의 파일명으로 변경
- 파일명에서 경로 문자와 특수문자 제거
- 파일 크기와 업로드 횟수 제한
- 업로드 파일에 대한 악성코드 검사

#### 서버 설정 관점

- 업로드 파일을 웹 루트 외부에 저장
- 업로드 디렉터리의 PHP 및 스크립트 실행 차단
- 업로드된 파일 URL에 대한 직접 접근 제한

## 환경 변수 및 API 키 보안

AI Scanner는 OpenAI API를 사용하므로 API 키가 필요합니다. API 키는 코드에 직접 작성하거나 GitHub 저장소에 커밋하지 않습니다.

```env
OPENAI_API_KEY=your_api_key
```

실제 `.env` 파일은 저장소에서 제외하고, 필요한 환경 변수 이름만 `.env.example`을 통해 공유합니다.

```gitignore
.env
.env.*
!.env.example
```

> [!WARNING]
> 실제 API 키, 내부 IP 주소, 계정정보, 세션 쿠키 및 데이터베이스 접속정보를 저장소나 증적 이미지에 포함하지 마세요.  
> 키가 노출된 것으로 의심되는 경우 즉시 폐기하고 새로운 키를 발급해야 합니다.

자세한 내용은 [OpenAI API Key Safety 공식 안내](https://help.openai.com/en/articles/5112595-best-practices-for-api-key-safety)를 참고하세요.

## 프로젝트 성과

### 기술적 성과

- Apache, PHP, MariaDB 기반 가상 사내망 서비스 구축
- Kali Linux 기반 모의해킹 환경 구성
- Burp Suite를 이용한 HTTP 요청·응답 분석
- SQL Injection을 통한 로그인 및 검색 조건 우회 검증
- Stored XSS 및 Reflected XSS 탐지·재현
- File Upload 검증 우회를 통한 WebShell 실행 확인
- 웹 서버 프로세스 계정 `www-data` 권한의 명령 실행 확인
- OpenAI API 기반 취약점 후보 분석 기능 구현
- 수동 증적 기반 AI 재진단 흐름 구성
- 진단 가이드, 최종 보고서 및 시큐어 코딩 가이드 생성
- 보고서 PDF 변환 기능 구현 및 정상 작동 확인

### 보안 관점의 성과

- 페이지별 SQL 쿼리 구조 분석의 중요성 확인
- 입력값 검증과 출력 인코딩의 차이 이해
- Prepared Statement 적용 필요성 확인
- 업로드 확장자 블랙리스트 방식의 한계 확인
- 업로드 경로의 스크립트 실행 권한이 미치는 영향 이해
- 자동 진단 결과의 오탐 및 미탐 가능성 분석
- AI 분석 결과에 사람의 검증이 필요한 이유 확인
- 검증 가능한 증적과 보고서 작성 과정 경험

### 협업 관점의 성과

- 기능별 담당자와 진행 상태를 Notion 데이터베이스로 관리
- 담당자별 최종 코드와 이전 버전을 구분하여 기록
- SQL Injection, XSS 및 File Upload Cheat Sheet 공유
- 취약점별 증적을 공동으로 수집하고 발표 자료에 활용
- GitHub에 통합된 최종본을 Kali Linux에서 재검증

## 한계 및 개선 방향

### 현재 한계

- 모든 페이지 및 파라미터를 자동으로 탐색하지 못할 수 있음
- 로그인 및 권한이 필요한 페이지의 자동 분석 범위가 제한됨
- File Upload와 같이 여러 단계가 필요한 취약점을 미탐할 수 있음
- 응답 차이만으로 취약점을 판단할 경우 오탐이 발생할 수 있음
- AI가 생성한 보고서 문구와 위험도는 보안담당자의 검수가 필요함

### 개선 방향

- 인증 세션을 유지하는 자동 크롤링 기능 강화
- 페이지별 폼과 파라미터 자동 식별
- `multipart/form-data` 기반 업로드 요청 분석
- 업로드 이후 파일 경로와 실행 여부 자동 추적
- 정상 요청과 공격 요청의 비교 기준 고도화
- 취약점별 재현 규칙과 신뢰도 평가 개선
- 오탐 및 미탐 사례를 테스트 데이터로 축적
- 수정 전후 동일 요청을 이용한 재검증 자동화
- 보고서의 민감정보 자동 마스킹 기능 추가
